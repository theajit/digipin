# PinID migration plan — PR-00

Status: proposed; there is no SQL migration or database change in PR-00. The audited main branch has no persistent application database. Production infrastructure/data outside this repository has not been inspected, so absence in source is not proof that production has no records. Never import the separate UI checkouts or touch another repository's data implicitly.

## Baseline and migration contract

Legacy encode/decode is stateless. Add PostgreSQL/Redis/OIDC/KMS configuration behind disabled PinID routes/features after review. Missing PinID configuration must not break the legacy encoder. When PinID is enabled, incomplete keys/provider/database configuration must fail startup or sensitive readiness, never weaken authorization. Bootstrap admin through a reviewed operational process, not a public endpoint or hardcoded secret.

Use numbered SQL files, a `schema_migrations(version, checksum, applied_at)` table and a dedicated migration role. One runner acquires a PostgreSQL advisory lock. For each unapplied file, run DDL plus version insertion transactionally; rerunning skips identical applied versions and aborts if checksum changed. Do not use broad `IF NOT EXISTS` to hide incompatible schema drift. Numbered files are immutable after release. Concurrent-index steps requiring nontransactional DDL are explicitly marked and have resumable detection/repair. No migrations run opportunistically in every application worker.

## Planned sequence (review before implementation)

| Version | PR | Additive work |

| 001 | PR-01 | users, namespaces, invitations, aliases, baseline audit_events and unique/composite constraints; seed controlled namespace and reserved-name policy |
| 002 | PR-02 | encrypted locations, owner/version indexes, wrapped-key metadata; no plaintext coordinate/DIGIPIN columns |

| 004 | PR-05 if needed | approved retention/deletion-job metadata and operational indexes, driven by measured workloads |

UUIDs generated by the application/platform; decide required PostgreSQL extensions explicitly, not by assuming superuser privileges. All records use UTC. For future tables with existing data, add nullable columns, deploy dual-read/write, backfill in bounded idempotent batches, validate constraints and only then enforce NOT NULL. Large indexes use concurrent creation with lock/time budgets; list indexes include owner, status, created_at and UUID. Unique alias constraints must apply to normalized names including tombstones.

There is no legitimate alias/location backfill from the legacy stateless endpoints. Any future import requires proof of user ownership/consent, dry-run counts, mapping rules, source inventory and approval. Do not infer addresses from access logs or silently create PinID accounts for KitchenOS customers.

## Deployment and compatibility

1. Inventory actual production hosts, database schemas, existing integrations and backups; confirm independent PinID ownership, TLS issuer and KMS permissions.
2. Take encrypted predeployment backup and prove restore in isolated staging. Record migration checksum manifest and application image/version.
3. Apply additive schema with dedicated runner, bounded lock timeout and observable failure. Disable public registration and PinID retrieval until verification completes.
4. Deploy app compatible with both the prior and current schema during rollout. Configure feature gate, scopes, client allowlists, secret manager and privacy-preserving proxy logs.
5. Run legacy GET/POST regressions, readiness checks and tenant-negative tests before enabling invited users. Enable KitchenOS only after provider/grant checks pass.
6. Monitor sanitized failures, rate-limit events and latency without payloads. Stop rollout on migrations, decryption or authorization failures.

## Verification matrix required when SQL exists

PR-01: empty database installs 001; reapplication changes nothing; two runners do not race; changed checksums abort; unique alias and verified-invite redemption races yield one winner; failure after consuming invite rolls back all writes. Test least-privilege runtime permissions and admin bootstrap denial from public routes.

PR-02: fresh install to 002 and upgrade 001 -> 002; existing identities survive; owner isolation, canonical validation, encrypted-at-rest inspection, nonce/AAD tamper rejection and key-version rotation/restore. Interrupted future backfills resume without duplication.

PR-03: fresh install to 003 and upgrade 002 -> 003; inconsistent client/owner/location relationships fail; concurrent retrieval/revocation behavior matches documented linearization; expired rows denied without cleanup dependency.

For every migration: transaction rollback on injected error, checksum/status output, schema comparison after rerun, previous application compatibility, concurrency/time-budget checks and isolated restore. Run these against real PostgreSQL, not an in-memory mock. Redis ephemeral state can be lost without erasing identity/consent truth. PR-00 can establish only that no migration is present; no clean-database or upgrade checks are claimed executed.

## Rollback and backup

PR-00 rollback: revert its docs/tests/checks/CI/package script/OpenAPI changes; runtime behavior and database are unchanged. Preserve user-local lockfile/UI work.

Future application rollback: disable PinID entrypoints, deny address retrieval, deploy prior compatible image and leave additive tables intact. Do not run DROP/TRUNCATE/down migrations in production. Restore database only for corruption/disaster, not routine rollback; quiesce writes and reconcile newer records before any restore. Destructive cleanup needs a separate reviewed change and retention approvals.

Backups are encrypted, access-restricted, versioned and tested with KMS/issuer configurations. Proposed objectives for review: RPO <= 15 minutes, RTO <= 4 hours; these are targets, not measured guarantees. Keep a restricted deletion ledger outside the restored snapshot so erased/suspended users and revoked grants cannot reappear after restore. Apply ledger before serving traffic; restoring without reconciliation stays offline. Key destruction needs a verified cryptographic-erasure process and backup key inventory. Document backup expiry, lawful retention exceptions and incident access.
